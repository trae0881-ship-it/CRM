Automatic link generation

Adometa keeps an inventory of actual application routes and uses the active canonical hostname for supported public links, authentication redirects, and page metadata.

1. What changes automatically

  • The shared route registry supplies page paths for the Super Admin link inventory and public sitemap selection.
  • The URL helper builds application URLs from the current origin in local development and the verified primary domain in production.
  • Signup confirmation and password recovery links request the canonical application URL.
  • The invite function consults the public canonical-domain configuration when that RPC is deployed.
  • Public route metadata sets canonical, Open Graph, Twitter, and website structured-data URLs at runtime.

2. What is not automatically changed

  • Supabase Site URL, redirect allowlists, and OAuth provider callback settings are project/provider settings. Update them manually and test them.
  • Hosting DNS records, domain attachment, TLS issuance, and server-side HTTPS redirects remain in the hosting provider dashboard.
  • External APIs, email systems, and third-party webhooks retain their provider-specific origins unless explicitly configured.
  • The hosted database API may be on a different origin; private API paths are visible only to a verified Super Admin.

3. Inspect the route inventory

Sign in as a Super Admin and open /saas/admin/domains/links. Search by page name or group. The route column represents the route observed in the application router; workspace tabs share /dashboard and are not presented as invented URLs. API entries show the configured API origin, if present, and are not public application pages.

“Available” describes the route registry entry, not a live response check. Use the explicit HTTP check when offered and independently test authentication and browser flows.

4. Domain change sequence

  1. Connect and verify a domain and TLS certificate.
  2. Set a verified active hostname as primary.
  3. Configure redirects in both Adometa and the host provider without creating conflicting rules.
  4. Update Supabase and OAuth redirect allowlists manually.
  5. Test confirmation, recovery, and invitations with real test accounts.

5. Local and staging environments

Localhost keeps its current origin so local development does not redirect to production. Use a separate staging host and separate Supabase project/settings where possible. Do not make a staging hostname primary in a production environment.
